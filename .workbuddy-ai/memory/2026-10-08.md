## 抽卡爆裂揭示动画（GachaBurstReveal）

新增 `src/components/GachaBurstReveal.tsx`，改造 `GachaPage.tsx` 抽卡结果展示。
旧流程抽完卡只弹一个 toast，**没有任何结果界面**；现在完整链路是：
餐盖掀开 → 光点从餐盘爆裂飞出 → 光芒消散 → 食材原地揭示 → 飞入下方「食材库」网格。

### 需求决策（用户确认）
- 播放层级：全屏覆盖层（非餐盖内局部、非两段式跨组件）
- 光点质感：纯白光点 + `mix-blend-mode: screen` 发光
- 结果呈现：食材先原地揭示，再飞入食材库（不做结果大卡）
- 时长：固定值，不分稀有度分级
- 十连重复食材：全部飞过去叠放
- 覆盖层背景：**暗场**（用户从三个方案里选的）

### 关键踩坑记录（改这块前必读）

1. **screen 混合与亮背景的物理冲突**
   页面背景是 `#c0fa1a` 亮柠檬绿。`screen(白, 亮绿)` = 白，白色光点在上面
   不会发光而是过曝成死白、完全看不见。所以覆盖层必须压暗底。
   这是阶段性暗场（仅揭示那 1.6~2.4s），不是把整站改暗。

2. **层叠上下文逃逸 —— 必须用 createPortal**
   覆盖层原本就地渲染在 `#gacha-page-root` 内，被嵌在 `<main>` 里 7 层深。
   底部导航是 `<main>` 的**兄弟**（z-40），而 `<main>` 自身无 z-index，
   所以覆盖层的 z-60 被封在 `<main>` 的层叠上下文内，**永远压不过导航**
   （截图表现为覆盖层只盖到 y≈1000，导航整条亮白露出）。
   → 解法：`createPortal` 挂到 `document.body`，配合 `fixed inset-0 z-[60]`。

3. **动画中途改目标会留下残余位移**
   原本用 `useState({394,790})` + `useEffect` 挂载后测量改写 `layerSize`，
   而 `layerSize` 参与计算结果卡锚点 → 动画跑到一半被改目标，
   Framer Motion 从当前位置插值到新位置，残留 **-127px** x 偏移，卡片被推出屏幕。
   → 改为惰性初始化 `useState(() => window.innerWidth)`，挂载后不再改。

4. **单抽 offsetX 未归零**
   `offsetX` 原来无条件按 4 列网格算，单抽 idx=0 得 `(0-1.5)*84 = -126px`，
   卡片整体左移出屏（实测 left 从预期 87 掉到 -42）。
   → 单抽必须把 offsetX 也归零。

5. **光点尺寸用 px 不用 vw/vh**
   覆盖层 portal 后铺满视口，但 vw 在桌面预览下与手机框宽度不一致，
   比例会失真。按视口尺寸换算成 px。

6. **光点必须垫在结果卡下层**（粒子 `z-0`、卡片 `z-10`、提示 `z-20`）。
   否则白色 screen 混合糊在白色卡面上过曝成死白，名称/kcal 全读不清。

7. **十连网格必须留安全边距**
   首版 5×74px + 4×8px 间隙 = 402px，在 390px 视口下最左/最右列被裁掉一半。
   → 改为 62px 卡宽 + 10px 列距 = 350px，两侧各留 20px。

8. **十连不能用和单抽一样的时长**
   统一 620ms 起飞时，十连网格还没铺开就开始缩（截图里只有一团重叠小方块）。
   → 拆成两套固定节奏：单抽 380/620/1600，十连 380/1250/2400（多 630ms 看清窗口）。

9. **飞行落点要校验是否在视口内**
   食材库网格在手机上常有一半在折叠线以下，`getBoundingClientRect` 照样返回坐标。
   不校验的话食材会飞向屏外看不见的点，表现为"缩小着飘到角落消失"，比原地淡出还难看。

### 与旧逻辑的耦合注意
- 入库（`setPantry`）与勾选推迟到**动画播完后**（`handleRevealComplete`）执行。
  不能在动画开始时就入库 —— 入库会立刻往网格插新卡片导致重排，

- 「跳过动画」勾选时仍走旧的 650ms 直接入库分支，不播覆盖层。

### 为什么要重做发光（关键设计教训）
单层白→黄→透明渐变铺在**白瓷盘**上、背景又是 `#c0fa1a` 亮柠檬绿 = **零对比度**，
看起来像「盘子脏了一块」而不是发光。删掉食物后这个问题暴露得非常明显。
→ 改为三层叠光，靠**溢出盘沿的 bloom** 才读得出「光」：
1. `dishBloomHalo`（新渐变）大椭圆 `rx=150 ry=46` —— 光晕溢到盘子轮廓之外
2. `dishRadiantGlow`（原渐变）中椭圆 `rx=112 ry=26` —— 光床
3. `dishCoreHot`（新渐变）小椭圆 `rx=42 ry=13` + 纯白 `rx=20 ry=7` —— 白热核心
外层套 `motion.g` 做呼吸脉动（opacity 0.82↔1、scale 1↔1.05，2.6s 循环）。

## 抽完卡餐盖自动盖回（并修掉一个既有位移 bug）

用户要求：抽卡结束后餐盖回到原来盖着的状态。

### 改动
原先 `isClocheOpen` 只在 `onTap` 里复位 —— 抽完盖子**一直开着**，
用户必须再点一次盖子才会关（而且那一次点击只关盖、不抽卡，白白浪费一次点击）。
`GachaPage.tsx` 补两处复位：

| 位置 | 时机 |
|---|---|
| 跳过动画分支（650ms 的 setTimeout 内） | 抽完立刻盖回 |
| `handleRevealComplete`（覆盖层退场回调） | 正常动画播完盖回 |

**为什么正常分支放在 `handleRevealComplete` 而不是 `setIsDrawing(false)`（1350ms）**：
`0–1350ms` 是「餐盖已掀开、盘内纯光可见」的展示窗口，那段时间必须保持掀开；
覆盖层退场才是整段演出的终点。

### 顺带修掉的既有 bug：餐盖关不干净（残留右偏 27px）
`FoodCloche3D.tsx` 的 `cloche-lifting-dome` 把**两种动画揉在了一个 motion.g 上**：
- 掀盖：`{x:32,y:-88,rotate:-29}` + 一次性弹簧
- 待机呼吸：`{x:0, y:[0,0,-5,-4,0,0], rotate:[0,0,-4,-3.5,0,0]}` + **`repeat: Infinity`**

关盖时 `isLifted` 变 false，直接复用了带 `repeat: Infinity` 的 transition，
于是 `x: 32 → 0` 的归位被无限循环反复重放。
实测（抽卡后采样 10s）：`domeX ∈ [133.5, 161.3]`，而正常待机应为 `[130, 134.7]` —— **最多右偏 27px**。

> 这是**既有 bug**，手动点盖子关闭也会中招；只是以前没人关盖子，所以没暴露。

修法：加 `domeSettled` 状态位，关盖先用一次性弹簧归位，
`onAnimationComplete` 里再 `setDomeSettled(true)` 切到呼吸循环；
`useEffect` 在 `isLifted` 变 true 时把它重置回 false。
（注意：`FoodCloche3D.tsx` 原先只导入了 `useEffect`，这次补了 `useState`。）

### 验证结果
- 包络对比（同一页面内多次采样取 min/max，避免采到呼吸动画的某一相）：
  抽卡前 `x=[130,134.8] y=[121.6,132]`，抽卡后 `x=[130,135.1] y=[121.6,132.5]` → **区间重合，无残留位移**；
  `y` 摆幅 10.9px → 呼吸动画正常恢复（不是静止不动）。
- 合盖轨迹：正常分支在覆盖层退场（3483ms）前后从 `(9,-24)` 平滑收到 `(0,0)`，约 400ms；
  跳过动画分支 421ms 掀到 `(33,-91)` → 784ms 起收 → 1322ms 归零，即「快速掀一下再盖回」。
- 两分支终态 `x=0`；控制台零报错；`tsc --noEmit` 与 `npm run build` 通过。

## 餐盖开启动效重做（用户反馈「太卡」，参照 motion-web/handfeel.md）

### 根因一：首次 `new AudioContext()` 阻塞主线程 230ms（这才是「卡」的主因）
用 `PerformanceObserver` 抓 longtask + 页面内 rAF 采样，定位到点击后 **214ms 完全掉帧**，
对应一条 **210ms longtask**。逐层排除后确认是 AudioContext 构造：

- 项目里有**两套各自独立**的音效，都在按下/掀盖那一刻 `new AudioContext()`：
  `GachaPage.playPressSound()`（按压音）与 `FoodCloche3D` 的掀盖水晶音。
- 实测**首次**构造阻塞 **230.3ms**，之后只要 **0.1ms** —— 成本全在第一次。
- 两处都只 new 不 `close()`：抽 3 次攒 6 个实例，Chrome 每页上限约 6 个，超了直接抛异常 → 音效失效。

**修法**：新建 `src/utils/audioContext.ts` 提供全局单例 `getAudioContext / warmUpAudio / resumeAudio`，
两个调用点都改为复用；用 `requestIdleCallback`（timeout 1500）把创建成本挪到页面空闲期；
播放时只剩 `resume()` + 排振荡器。
→ 掉帧 **214ms → 54ms**，longtask **210ms → 54ms**，且抽 3 次后构造次数恒为 **1**（无泄漏）。

> ⚠️ 排查时踩的坑：一开始以为单例没生效（构造次数仍每次 +1），
> 加了模块加载计数器才发现模块只执行 1 次、单例确实命中 ——
> **是 GachaPage 那第二套音效在新建**。定位「谁在 new」比盯着自己的代码猜有效得多。

### 根因二：掀盖只有「一个弹簧」，读起来是平移不是掀开
`handfeel.md` 的诊断表 + 组合律明确写：只有 §1 位置弹簧 = 「顺但是没劲」，
§2 速度耦合与 §4 次级运动才是读出重量感的东西。原实现 `x/y/rotate` 同相位，三轴一起走完，
所以像「整体被推走」。

**修法**（`FoodCloche3D.tsx` 的 `cloche-lifting-dome`）：改为 5 关键帧 + `times` + 逐段 `ease`：

| 节拍 | times | x / y / rotate |
|---|---|---|
| 静止 | 0.00 | 0 / 0 / 0 |
| 下压预备 | 0.13 | -4 / **+5** / **+3**（反向微蹲） |
| 垂直起抬 | 0.42 | 12 / -52 / -14 |
| 弧线外摆 | 0.74 | 34 / **-94** / **-33**（过冲） |
| 回稳 | 1.00 | 32 / -88 / -29 |

时长 0.86s（必须早于 `GachaPage.tsx:349` 那个 1350ms 的覆盖层接管点）。
**核心是错峰**：y 在 0.42 时已走完 60%，而 x 只走 38%、rotate 只走 48%
—— 实测 y 到 -52 是 357ms、x 到 +20 是 525ms，**y 领先 x 168ms**。
这个「垂直先行、水平与旋转滞后」就是「盖子被抬起来」与「被平推走」的区别。

### 根因三：光是「弹出来」的，不是「漏出来」的
原 `plate-revealed-delicacy` 用 `scale 0.65→1 + opacity 0→1` 的通用 pop。
**修法**：亮度 200ms 快速拉起（餐盖还在起抬，光已先亮 → 盖子让开多少就露多少，
真正的「揭示」由餐盖运动完成）；缩放起点从 0.65 收到 0.88（0.65 的 pop 感太像贴纸）；
另加一记**一次性爆发闪光**（`motion.ellipse`，0.8s 内 `[0, 0.95, 0.3]`）作为「光炸出来」的冲击感；
星点加外层 `[0.75, 1.3, 1]` 的一次性外推（§4 次级运动，让画面不是只有主角在动）；
内腔 `cloche-interior-cavity` 由硬切改为 `motion.g` 淡入。

## 掀盖幅度改小：右侧铰链单侧微开（用户反馈「打开幅度太大，很难看」）

上一版把盖子抬到 `(x 32, y -88, rotate -29°)` —— 整个飞离盘子，确实过头了。
用户要的是「轻微单侧打开露出光」。

### 关键根因：旋转轴心算错了，落到了盘子外面
原写法是 `transformOrigin: '280px 222px'` + **`transformBox: 'fill-box'`**。
`fill-box` 会让这两个长度变成「**相对元素包围盒左上角**的偏移」，
而穹顶包围盒左上角约在用户坐标 (78, 52)，于是实际轴心落到 **(358, 274)**
—— 盘子右下方的**外面**。绕一个盘外的点旋转，自然会把整个盖子甩出去。

**修法**：改成 `transformBox: 'view-box'`（SVG 的默认值）+ 用户坐标 `transformOrigin: '322px 216px'`。
(322, 216) 正好是穹顶底缘（`rx=122 / cy=216`）的**右端点**，即盖子压在盘沿上的位置。
绕它旋转就是标准的「右侧铰链、左边缘抬起、右边缘始终压住」。

> 教训：SVG 上做铰链旋转，**别用 fill-box 配像素值**。
> fill-box 的百分比是相对包围盒的，但长度是相对包围盒左上角的绝对偏移，
> 和「viewBox 用户坐标」完全是两套语义，混用必错。

### 新姿态
```
x:      0                        （铰链动作不产生水平位移）
y:      [0, 2, -2, -6, -4]       （只有几像素，位移刻意滞后于旋转）
```

## 修透视：`rotate()` → `scaleX + skewY`（用户：「有透视问题，不像是餐盖在盘子上打开」）

### 根因
之前用的是**屏幕平面内的 `rotate()`** —— 等于把穹顶当成一张贴纸在二维里转。表现是：
穹顶底缘变成一条斜直线、轮廓整体刚性跟着甩、底面和盘子椭圆脱开。

### 正解：绕左端点的三维铰链，在正交投影下等价于一个**错切**
盘面椭圆 `rx=155 / ry=30` → 相机仰角 `sinφ = 30/155 = 0.1935`、`cosφ = 0.981`。
盘面内一点绕左端点 (78,216) 转 θ 后投影为：
```
sx' = sx · cosθ
sy' = sy − sx · sinθ · cosφ
```
即 `scaleX(cosθ)` + `skewY(−atan(sinθ·cosφ))`。
**错切后的椭圆仍然是椭圆**，所以底面会读成「三维里的圆」，而不是被转歪的平面图形。

### ⚠️ 符号：传正角才是右边缘抬起
屏幕 y 向下，右边缘 `sx>0` 要变高就得 `sinθ>0`，所以 **θ 为正**。
（我在扫描脚本里一开始写成负角，得到 `b=+0.3355`，而组件实际是 `b=−0.3356`，
自己把自己带偏了一轮。**改这块先量矩阵，别靠直觉。**）

### 数值换算表（θ 与两个值的对应，改角度必须同时重算）
| θ | scaleX = cosθ | skewY = −atan(sinθ·0.981) |
|---|---|---|
| +2.5°（预备反向） | 0.9990 | +2.45° |
| +7° | 0.9926 | −6.82° |
| +16°（过冲） | 0.9613 | −15.13° |
| +14°（回稳） | 0.9703 | −13.35° |

### 角度 20° → 14°
换成正确投影后，**同样的角度视觉位移大得多**（盖子远端按 sinθ 抬起，
而屏幕旋转只是让轮廓歪一点），20° 会读成「盖子从盘上滑走」。降到 14° 才既看出打开又仍坐在盘上。

### 验证：逐点核对投影
把正确投影的四个基准点手算出来，与 `scaleX + skewY` 的实际输出比对，**完全吻合**：
| 基准点 | 正确投影 | 实测 |
|---|---|---|
| 右端 | 158.1 | 158.1 |
| 前端 | 210.65 | 210.65 |
| 后端 | 163.45 | 163.45 |
| 左端（支点） | 216（不动） | 216 |

矩阵实测 `[[0.9703, 0], [−0.2373, 1]]`，与 `scaleX(cos14°) + skewY(−13.35°)` 一致。

## 最终定稿：纯刚体（用户：「不要产生形变」）

上一步的 `scaleX + skewY` 虽然投影数学正确，但**会把穹顶轮廓压扁** —— 那就是形变。
用户明确不要。于是退回**纯刚体变换：只有位移 + 旋转**。

### 三版的取舍（改这块前必读）
| 版本 | 变换 | 用户反馈 |
|---|---|---|
| ① 屏幕平面 `rotate()` | 刚体，但绕支点硬转 | 「有透视问题，不像在盘子上打开」 |
| ② `scaleX + skewY` | 数学正确的三维铰链投影 | **「不要产生形变」**（轮廓被压扁） |
| ③ **纯刚体：抬起为主 + 小角度旋转** | 当前 | — |

### ③ 的具体数值
```
x:      0
y:      [0, 2, -14, -34, -30]   ← 位移为主，造出读作「打开」的缝隙
rotate: [0, 2, -3, -9, -7]      ← 绕左端点的小角度旋转，保留「以最左边为支点」的单侧感
```
- 角度压在 **7° 以内**：再大就读成「盖子被转歪」而不是「掀开」。
- 位移先行（0.42 时 y 已到 -14，rotate 才 -3）。
- 待机呼吸改为**纯位移不旋转** —— 支点在左端，绕它转会让右边缘翘起来「像盖子松了」。

矩阵实测 `a=0.9925, b=-0.1219, c=0.1219, d=0.9925`，**正交**（无缩放无错切）。
穹顶包围盒高度从错切版的 199 恢复为刚性尺寸。

### 教训
**「投影正确」和「观感可接受」是两件事。** 错切在数学上是对的，

## 加「扑腾几下再打开」（用户：「改成餐盖来回扑腾几下再打开，参考优秀案例」）

### 参考到的业界结构
查了两处开箱动画资料，结论一致 —— 这是个有名字的模式：**「Shake & Open」**。
- `webdevpuneet` 的开箱揭示：先加 `.shaking` 类触发 CSS `shake` 关键帧
  （**交替 translateX + rotate**）配脉动光环，**循环约 1.4s 蓄势**，再 `.burst` 爆开。
- `echohtp/animation-demos` 的 8 种开箱模式里第 7 种就叫 **Shake & Open**，
  生命周期明确分五态：`Idle → Anticipation（点击后短暂脉冲）→ Opening → Revealing → Claimed`。

**两个可借鉴要点**：
1. **抖动要双轴交替**（只抖单轴会读成机械往复）；
2. **振幅递增**，从小抖到大抖，张力才堆得起来。

### 实现（`FoodCloche3D.tsx`）
三段式，仍是**纯刚体**（无缩放/错切）：扑腾 0.52s + 掀开 0.88s = **总时长 1.4s**。

```
y:      [0, -1.5, 0.5, -2.5, 0.5, -4,  0.5, -2,  -34, -30]
rotate: [0, -3.5, 0,    -7,   0,  -11,  0,   -3,  -12,  -8]
times:  [0, 0.05, 0.11, 0.18, 0.24, 0.31, 0.37, 0.45, 0.64, 1]
```
- **振幅递增**：−3.5° → −7° → −11°，最后一次几乎接近掀开角（−12°），
  读成「快顶不住了」，然后才真的掀开。
- **每次「砸下」回到 0**（拍回盘面），才有「盖不住」的挣扎感；
  砸下的缓动用 `[0.55, 0, 0.85, 0.4]`（加速砸向盘面，出冲击感）。
- **扑腾段 y 振幅只有 4px** —— 盖子是在盘上拍，不是浮起来拍。位移留给掀开段。
- 待机呼吸仍是纯位移不旋转。

`GachaPage.tsx` 的 `setTimeout(..., 1350)` → **2000ms**。
